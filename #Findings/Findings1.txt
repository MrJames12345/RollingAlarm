1. createInBackground utilization
UI / main isolate
`_openConnection()` returns `NativeDatabase.createInBackground(file, setup: …)`. Queries from the Riverpod-held singleton run on Drift’s worker isolate, so UI frames are not blocked by SQLite I/O.

main() calls resolveDatabasePath() before `RA_Database()`, so `_getDatabaseFile()` does not fall through to the `.` fallback at startup.

Alarm / widget isolates
`openForIsolate` intentionally uses synchronous `NativeDatabase`. Those callbacks already run off the UI isolate; `createInBackground` would only add another hop.

Do not require createInBackground “for all background operations.” The right rule is: offload from the UI isolate; open sync (or a dedicated isolate connection) where you already are background.

R2: exception path
When `onDidReceiveNotificationResponse` fires in the foreground, `handleNotificationResponse` still calls `openForIsolate`, opening a second sync connection on the main isolate beside the long-lived createInBackground executor. Prefer reusing `RA_DatabaseProvider` when a Flutter binding / ProviderScope exists, and reserve openForIsolate for true headless entry points.
2. WAL and busy timeouts
PRAGMA setup (both openers)
Identical setup on UI and isolate paths:

`PRAGMA journal_mode = WAL;` then `PRAGMA busy_timeout = 5000;`

This is the right pair for concurrent readers (UI watch / get) plus short writers (alarm isolate log + state). SQLite will wait up to 5s on SQLITE_BUSY instead of failing immediately when the other connection holds the write lock.

Note: busy_timeout does not serialize application-level read-modify-write. It only prevents hard lock errors during overlapping physical writes.

Memory leak verdict on .watch() providers
No leak found in the Drift StreamProviders. `autoDispose` cancels the Riverpod subscription, which cancels Drift’s query stream. Family providers (per routineId / nextTriggerTime) tear down when cards or pages unmount. The DB singleton is deliberately not autoDisposed.
Cross-isolate watch coherence
Isolate writes are invisible to the UI connection’s in-memory cache unless notified. `registerUiPort` correctly calls `database.notifyUpdates` for all three tables after alarm pings, so active `.watch()` streams refresh without polling.

Recommended fixes (priority order)
Wrap handleTransition’s state update + log insert in `db.transaction()`, and gate concurrent transitions per routineId (e.g. SharedPreferences lock key or compare-and-set on IsRinging / snooze count) so UI and watchdog cannot both commit.

Split notification handling: if WidgetsBinding / UI DB exists, use RA_DatabaseProvider; only call openForIsolate from the `@pragma('vm:entry-point')` background handler.

Add a unique index on RoutineStates.RoutineId (and prefer getSingleOrNull after enforcing uniqueness).

Dedupe AlarmRingPage pushes in HomePage listen (track navigated routineId or check an existing route). Assert `_resolvedDbPath != null` in `_getDatabaseFile` instead of the `.` fallback.

What is already solid
createInBackground for UI, WAL + 5s busy_timeout on both openers, try/finally closes on isolate DBs, IsolateNameServer notifyUpdates for watch refresh, and autoDispose StreamProviders over Drift .watch() with no keepAlive retention.
